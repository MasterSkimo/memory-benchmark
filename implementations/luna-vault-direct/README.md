# Luna direct Markdown vault

This candidate exposes only list, read, and search operations over Markdown in one fixed organization/project directory. It creates no database, graph, embedding, or persistent index. Python 3.12.14 standard library only; no third-party SDK/backend versions.

`ScopedMarkdownVault(corpus_root, organization_id, knowledge_space_id)` fixes authorization at construction. Its native file-tool surface is `list_markdown()`, `read_markdown(document_id)`, and `search(question, top_k=5)`. Optional identity arguments are checked against the fixed identity. The search helper scans authorized Markdown at call time using lexical overlap for P1R; it is a deterministic retrieval control and **is not Luna**. E2E results count only fresh native Luna sessions that use this restricted surface.

Run interface integration tests:

```sh
PYTHONPATH=implementations/luna-vault-direct python3 -m unittest discover -s implementations/luna-vault-direct/tests -v
```

Run one P1R question per process (pass one frozen pilot record as JSON on stdin):

```sh
python3 implementations/luna-vault-direct/run_one.py fixtures/vault < one-question.json
```

For each P1E question, start a fresh native Luna session and provide only the answer policy in `config/codex/answer-policy.txt`, that one question, and the three operations bound to that question's fixed organization and knowledge space. Do not provide other questions or corpus directories. Capture the returned JSON answer and citations; leave token/tool counters null unless the native runtime exposes them. The wrapper reports its actual filesystem reads and bytes for tool use; it does not report model calls or claim to measure Luna telemetry.

The session's callable operation is one JSON object on stdin for each process invocation. The wrapper verifies the frozen vault SHA-256 before and after every operation and suppresses results if either digest differs. Integrity-guard reads and bytes are reported separately from wrapper file reads and bytes. For example, bind these arguments from the one question's record and use the appropriate operation body:

```sh
python3 implementations/luna-vault-direct/native_tool.py --organization-id org-alpha --knowledge-space-id project-01 --question-id q00-exact-0
```

Operation bodies are `{"op":"list"}`, `{"op":"read","document_id":"org-alpha/project-01/note-001"}`, or `{"op":"search","question":"...","top_k":5}`. The wrapper appends each invocation to `results/luna-vault-direct/events/<question-id>.jsonl`, including operation, status, elapsed time, filesystem reads/bytes and source IDs. It stops after 12 invocations for a question. The native runtime's model/tool telemetry remains null unless exported by that runtime.

Authorization is enforced at the API boundary, including identity mismatch, path traversal, non-Markdown files, symlinked scope components, files, and directories. Source frontmatter organization/project values are checked before returning evidence. `document_id` and `revision` come from the Markdown metadata. No OS sandbox is claimed; the native Luna tool must expose only this scoped wrapper.

## Reproduction and source

Implementation: `scoped_vault.py`; audited native tool: `native_tool.py`; single-question retrieval runner: `run_one.py`; integration tests: `tests/test_scoped_vault.py`. The benchmark source is the repository's `fixtures/vault`; its frozen source hash is recorded in `fixtures/manifest.json`. P1E answers and citations are in `results/luna-vault-direct/answer-traces.jsonl`, with one audited operation log per question under `results/luna-vault-direct/events/`. Run hashes, model alias and effort are recorded in `results/luna-vault-direct/manifest.json`. Native Luna was instructed to use only the wrapper; the platform did not provide a capability schema that strictly hid other tools. No answers were generated by the deterministic implementation.
