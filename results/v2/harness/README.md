# V2 harness contract

`benchkit/v2/harness.py` exposes `run_retrieval(candidate, adapter_path, corpus_path, questions_path, output_dir, frozen_manifest_path=None)` and the matching CLI. Candidate adapters must export `create_adapter(corpus, organization_id, knowledge_space_id)` and an adapter `.search(question_record, top_k=5)` returning `{hits: [{document_id, revision, score, text}], backend_calls, file_reads, bytes_read}`. The harness enforces top-k, exact revision presence, and the fixed `org/space/` document prefix; any escaped result is recorded as a tenant leak and stops that candidate.

The frozen manifest provides `questions_sha256`, `corpus_sha256`, and the ordered 40-element `question_ids` list. The corpus digest is SHA-256 over each sorted source's relative UTF-8 path, NUL, raw bytes, NUL. The runner verifies the corpus before and after every query and setup, records candidate implementation source SHA-256 values (excluding runtime/cache directories), setup separately from query time, wrapper counters separately from native-tool counters, and leaves unavailable counters null. It does not import evaluation or gold files. Outputs are `retrieval.jsonl` and `retrieval-summary.json`; scoring remains a separate step.

Native Luna answers use `benchkit/v2/answer_tool.py`'s `BoundAnswerTool`. Its coordinator-created config binds principal scope, question, corpus, session handle, and token digest. Tool requests cannot override org/project, paths, or tenant filters. Returned lists, reads, and hits are revalidated after adapter mapping, including their current source revision. It logs wrapper calls and integrity-guard I/O separately from backend calls. The launcher persists the per-question wrapper-call count in its audit file when tools invoke it as a subprocess.

## Native answer session broker

`python -m benchkit.v2.session_server --config <trusted-config.json> --port 0` binds only to `127.0.0.1`. It loads the candidate adapter once per authorized org/project from a coordinator-created config containing `candidate`, `run_id`, `adapter_path`, `corpus_root`, `corpus_sha256`, `events_root`, and 1–20 `sessions`. Each session entry has `question_id`, `organization_id`, `knowledge_space_id`, a random 32+ character `handle`, `token_sha256` equal to SHA-256(handle), and optional `max_tool_calls`. The broker offers no API to create or change sessions. It exposes only POST `/tool` and GET `/health`.

`python -m benchkit.v2.session_client --port <ready.port> --handle <handle> --request '{"op":"search","question":"...","top_k":5}'` calls the fixed session. It accepts no org, project, or path options. All candidates use the same scoped Markdown list/read implementation; only search delegates to the candidate adapter. Startup metrics live in `startup.json`. Per-question wrapper and transport events, exact request/response bytes and hashes, and native-counter nulls live under `events_root/<run_id>/<question_id>/`. Adapter/module startup remains separate from Luna answer-session wall time, which the native session dispatcher must measure.
